<scoring_contract>
## Locked thresholds, weights, and per-check rules (resolves A1 — required for the thin-band contract)

This phase's `test_thin_experiment_scores_thin` contract (Plan 01) requires a required-fields-only
record to land in band `thin` (composite < `PARTIAL_THRESHOLD`). Because the thin fixture is
defined required-fields-only (Plan 01: NO reviewer_model/critique, NO hardware, NO lessons,
NO recommended_action, NO completed_at) yet `local_model_output` and `eval_score` are schema-required
and always present, the weights and per-check semantics below are LOCKED (no longer "tunable A1")
so the thin record provably stays below 0.50.

**Thresholds (LOCKED):** `COMPLETE_THRESHOLD = 0.80`, `PARTIAL_THRESHOLD = 0.50`.

**WEIGHTS (LOCKED, sum == 1.0):**
| key | weight |
|-----|--------|
| output_present | 0.30 |
| reviewer_critique | 0.20 |
| model_metadata | 0.20 |
| hardware_present | 0.10 |
| lessons_learned | 0.10 |
| outcome_signals | 0.10 |

**Per-check rules (LOCKED — each returns a float in [0.0, 1.0]):**
- `_score_output_present` → 1.0 if `outcome.local_model_output` is present AND non-trivial
  (length >= a small threshold, e.g. >= 20 chars), else 0.0.
- `_score_reviewer_critique` → 1.0 if `outcome.reviewer_critique` is a non-empty string, else 0.0
  (Optional → 0.0, never error; Pitfall 2).
- `_score_model_metadata` → ADDITIVE presence over the three identity fields
  `local_model.model_name`, `local_model.quantization`, `local_model.provider`: fraction populated
  (e.g. only `model_name` present → 1/3 ≈ 0.333). Mirrors `score_metadata_completeness` additive idiom.
- `_score_hardware_present` → 1.0 if `record.hardware` is populated (e.g. `gpu_name` present), else 0.0.
- `_score_lessons_learned` → 1.0 if `outcome.lessons_learned` is a non-empty list, else 0.0.
- `_score_outcome_signals` → **0.0 when ONLY `eval_score` is present.** Specifically: this check
  scores `recommended_action` and `completed_at`, NOT `eval_score` (which is schema-guaranteed in
  range and is the *answer-quality* signal, not a completeness signal — Pitfall 4). Compute as the
  fraction of {`recommended_action` present, `completed_at` present} that are populated
  (each contributes 0.5; both absent → 0.0; both present → 1.0). Do NOT add any constant for
  `eval_score` being "in range" — a sane eval_score is the schema's job, not a completeness credit.
  This guarantees a required-fields-only record scores 0.0 here.

**Thin-band proof (must hold for the LOCKED values above):**
For the required-fields-only thin fixture: output_present=1.0, reviewer_critique=0.0,
model_metadata≈0.333 (only model_name), hardware_present=0.0, lessons_learned=0.0,
outcome_signals=0.0. Composite = 0.30 + 0.0 + (0.333·0.20≈0.067) + 0.0 + 0.0 + 0.0 ≈ **0.367**,
which is `< PARTIAL_THRESHOLD (0.50)` → band `thin`. The contract holds deterministically.
(If the thin fixture were to carry `quantization`/`provider` too, model_metadata would rise to
0.20 and composite to ≈0.50 — exactly why Plan 01 pins the thin fixture to required-fields-only.)
</scoring_contract>
