<critical_decision_constant_vs_lazy>
LOCKED migration strategy (resolves RESEARCH Open Question Q2 — derived from the existing test suite, NOT guessed):

The existing suite monkeypatches the MODULE-LEVEL CONSTANTS directly (~30 sites: `monkeypatch.setattr("kajiba.cli.KAJIBA_BASE", tmp_path)` in tests/test_cli.py; `monkeypatch.setattr("kajiba.config.ACTIVITY_LOG", ...)` in tests/test_config.py). It also monkeypatches `Path.home` (tests/test_config.py `fake_home`). Therefore:

1. MODULE-LEVEL CONSTANTS stay module-level constants, derived at import from get_hermes_home(): e.g. `KAJIBA_BASE = get_hermes_home() / "kajiba"`. This keeps every existing `monkeypatch.setattr(...KAJIBA_BASE...)` site working unchanged (they patch the constant, not the helper). Do NOT convert these constants to functions.
2. FUNCTION-BODY config.yaml paths go LAZY — call get_hermes_home() INSIDE the function body at use time: `_load_config_value`/`_save_config_value` (config.py:89,123) and the two cli.py config.yaml reads (cli.py:852,932). This preserves the existing `fake_home` monkeypatch (which patches Path.home) AND respects a HERMES_HOME set later. Replace `Path.home() / ".hermes" / "config.yaml"` with `get_hermes_home() / "config.yaml"`.
3. get_hermes_home() itself reads `os.environ.get("HERMES_HOME")` on EVERY call (never cached) so the new test_config.py setenv cases pass.

Self-check before finishing: run the FULL existing suite. If any pre-existing test regresses, the constant-vs-lazy split was applied wrong — fix the split, do not weaken the test.
</critical_decision_constant_vs_lazy>
