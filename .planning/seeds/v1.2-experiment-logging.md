# Seed: v1.2 Experiment / Eval Logging (Dual-Use)

Milestone seed produced by `/gsd-explore` on 2026-06-03. Captures the converged
direction so `/gsd-new-milestone` can formalize v1.2 with a rich starting point
instead of re-deriving it. Source proposal: `docs/dual-use-roadmap.md`.

## Vision

Evolve Kajiba from a single-purpose coding-session collector into a **dual-use
system**: keep the community coding-data pipeline, AND add a first-class layer
for **local-model experimentation/evaluation logging** — local model outputs,
reviewer-model critiques (e.g. Grok reviewing Nemotron/Qwen/Gemma), quality
drift tracking, and queryable lessons-learned that inform routing / prompt /
fine-tune decisions. Related work: AEON-7 deployments, a Hermes local-model
orchestration practice project.

## Converged decisions (from the explore interview)

1. **Timing / structure — Parallel milestone.**
   v1.2 stands up *now*, alongside v1.1 (not after, not by pausing v1.1). The
   parts that don't need the Hermes plugin start immediately. Driver: user needs
   the full eval-logging pipeline operationally soon, and is committing to it as
   first-class mission — so "defer to v2" and "fold a small slice into v1.1" were
   both rejected.

2. **Schema — Separate `ExperimentRecord` with a shared base.**
   Extract a common base out of `KajibaRecord`; both the coding-session record
   and `ExperimentRecord` extend it. Add a `record_kind` discriminator
   (`"coding_session"` | `"model_experiment"`). Do NOT bloat `KajibaRecord` with
   optional experiment fields (god-object risk), and do NOT fully duplicate.
   Exact field shape is deferred to v1.2 `spec-phase`. Candidate models from the
   source doc: `ExperimentMetadata`, `ExperimentOutcome`, optional
   `reviewer_turn` on a turn.

3. **Pipeline — Shared core, divergent tail.**
   - **Reuse:** schema base, scrub primitives.
   - **Branch:** an eval-specific scorer (coding-trajectory scoring does not
     apply), private local storage, analysis/export formats.
   - **Skip entirely:** the community publish path / HuggingFace upload —
     experiment data is **private/internal**.

4. **Roadmap impact — v1.1 stays intact; 6-7 become shared foundation.**
   v1.1 Phases 6-9 are unchanged. Phases 6 (plugin) and 7 (turn capture) are
   now understood as **shared capture foundation** serving both coding sessions
   AND live experiment capture. The "model evaluation = out of scope" boundary
   in REQUIREMENTS.md is **deliberately reversed** (now → v1.2).

## Scope of "soon": the FULL pipeline

User wants all of the source roadmap's capability in the near term, not just an
MVP slice: structured logging, the reviewer/critique workflow, drift tracking,
export formats, and the Nemotron/Qwen/Gemma practice-project integration.

## Input path: mixed (drives the v1.1 dependency)

Experiment records are created two ways:
- **Deliberate CLI/script logging** — `kajiba experiment log/start/review`.
  *Independent of v1.1* → can be built immediately.
- **Live Hermes capture** — eval runs inside Hermes orchestration sessions,
  captured via the same hooks. *Depends on v1.1 Phase 6-7* → gates on that work.

## Candidate phase breakdown (for /gsd-new-milestone to refine)

Mirrors the source doc's 5 phases, re-sequenced around the v1.1 dependency:

- **P-A · Schema & core types** *(no v1.1 dependency — start now)*
  Extract shared base from `KajibaRecord`; add `record_kind`; add
  `ExperimentRecord` / `ExperimentMetadata` / `ExperimentOutcome`. Migrate
  existing staged/outbox records (see research question).
- **P-B · Experiment CLI & deliberate logging** *(no v1.1 dependency)*
  `kajiba experiment` command group; programmatic logging entry point; private
  local store (separate namespace under the Hermes-home dirs).
- **P-C · Eval scorer & scrub tuning** *(no v1.1 dependency)*
  Eval-specific quality signals; relax redaction for model/hardware fields on
  experiment records while keeping aggressive PII scrubbing elsewhere.
- **P-D · Reviewer / critique + drift** *(no v1.1 dependency for deliberate path)*
  Attach reviewer-model critiques (Grok); structured vs. free-form
  `lessons_learned`; drift detection across runs.
- **P-E · Live experiment capture** *(GATES on v1.1 Phase 6-7)*
  Capture eval runs from live Hermes sessions via shared hooks.
- **P-F · Export & practice-project integration** *(after P-A..P-E)*
  Analysis/export formats (NOT community publish); wire the Nemotron/Qwen/Gemma
  workflow to write directly into experiment records.

## Open questions to resolve in spec/discuss

(Source doc §6, plus what surfaced in the interview.)
1. Storage namespace: separate dir tree for experiment records vs. coding
   sessions under Hermes-home? (Leaning separate, given private/internal.)
2. Base-extraction migration: how to convert existing `KajibaRecord` JSON to a
   discriminated-union shape without breaking staged/outbox files. (Captured as
   a research question.)
3. Multi-turn experiment conversations (local model ↔ reviewer) — supported how?
4. `lessons_learned`: free-form vs. structured categories (coherence /
   creativity / hallucination / ...).
